# AXON 3D 专业化改造方案

日期：2026-11-02。依据：当前 Three.js r187 源码、Blender 构建脚本、GLB 内容解析，以及本地浏览器中的机房和拓扑实景检查。本文件保留最初诊断。随后已完成基础校准与 R04 精修样板，实际改动与验证见 [交付记录](3d-comparison/README.md)，截图见 [交互对比](3d-comparison/index.html)。

## 1. 设计目标

机房采用克制、可信的工业数字孪生风格：真实尺寸、机柜结构、材质和照明承担主要视觉信息；颜色表达状态，光效只用于真实灯具和少量状态灯。拓扑采用可读的空间关系图，优先保证标签、路径追踪和影响分析。

建议继续使用现有 Blender → glTF → Three.js 管线。当前规模为 14 个柜位、26 台设备，先完善资产和渲染组织即可；暂不引入引擎迁移、云端渲染或实时路径追踪。NVIDIA DSX 可作为设施模型、设备和业务数据结合的产品参考，不能把其 RTX/仿真能力当作浏览器方案的现成能力。[官方参考](https://docs.omniverse.nvidia.com/dsx/latest/overview.html)

## 2. 当前“玩具感”的具体来源

| 观察/代码证据 | 对画面的影响 | 改造动作 |
| --- | --- | --- |
| `dc3d.js` 为设备整个外壳及面板设置 emissiveIntensity=0.9，灯条强度最高 3.2，再叠加 Bloom strength=0.85 | 当前画面出现大面积青白色光晕，遮住结构与材质 | 外壳不自发光；LED 和灯具进入独立辉光层；先关 Bloom 校准基础画面 |
| 机柜宽 0.62 m，沿排中心间距 2.8 m，留空约 2.18 m | 柜体像散放在展台上的小盒子，缺少连续机柜排的空间感 | 先确认模拟布局目标，统一修改布局源数据再导出；真实机房接入后必须保留测量坐标 |
| `build_dc_model.py` 的设备主要由机箱、面板和 LED 三块长方体构成；没有倒角、把手、盘位和接口层次 | 缺乏尺寸参照及边缘高光，近看也无法识别设备结构 | 建立模块化机柜/服务器资产库，补中尺度结构；细小孔洞交给贴图 |
| GLB 只有 1 张贴图，0 张法线、粗糙度、AO 贴图 | 大平面材质一致，金属、喷涂层、塑料、橡胶分辨不清 | 制作材质图集，烘焙法线与 AO，按材料区分粗糙度 |
| 主题色控制环境贴图、轮廓光、点光和整个设备发光 | 更换界面主题等于更换机房的物理材料和照明 | 物理场景保持中性照明；主题仅控制界面、选择标记与少量状态标识 |
| 机房与拓扑默认自动旋转；拓扑卡片和文字随观看角度压缩 | 用户尚未定位对象，画面已经改变；阅读像观看演示动画 | 默认固定构图，设置明确的视角按钮；自动巡航作为用户主动开启的演示功能 |
| 拓扑卡片顶部强发光，粒子持续流动，文字与 3D 一起经过后处理 | 亮条和粒子抢过标签，画面缺少主次 | 降低默认边密度，只突出当前路径；标签单独叠加，不参与 Bloom |

GLB 解析基线：551,028 字节，343 个节点，325 个 mesh，44 个材质，4,572 个三角形，1 个纹理。325 个 mesh 不等于实测 draw call，但“很多小网格、很少几何细节”说明资产组织仍有很大优化空间。当前没有完成 GPU 性能基准测试。

另有三个需要随 3D 改造修复的确定性问题：

1. **空调父子坐标重复平移。** `build_crac()` 给父对象和子部件都写入同一世界坐标。GLB 的 `CRAC_1_body` 世界 X≈−20.8，`CRAC_4_body` 世界 X≈20.8，而房间 X 范围为 −11～11。应让子部件使用相对父对象的局部坐标，并为导出场景加入边界检查。
2. **环境 RenderTarget 丢失所有权。** `env3d.js` 只返回 `rt.texture`，主题切换只调用 Texture.dispose。应保留 RenderTarget 并在替换时 dispose，释放相应缓冲。[Three.js 资源释放说明](https://threejs.org/manual/pages/how-to-dispose-of-objects.html)
3. **换主题累积告警材质列表。** `applyDevGlow()` 每次创建新的 `mats` 数组，然后以引用相等查重，无法命中旧数组；应每次重建列表或以设备 ID 索引。同时浏览器已有 `PCFSoftShadowMap has been removed` 警告，需要按本地 r187 的有效 API 调整。

## 3. 机房视觉规范

### 空间与镜头

- 全管线保持米制、统一原点和轴向；设备继续按 U 位映射。变更布局时同步二维布局、GLB 与拾取映射。
- 第一屏采用稳定的建筑剖切总览，能看见两排柜体和冷通道；提供“总览 / 通道 / 机柜”三个视角。
- 通道视角以约 1.6 m 观察高度作为试调起点；近景以机柜和设备为目标点，限制穿墙、穿柜及极端俯仰角。
- 墙和通道顶盖可按视角隐藏或剖切；保留支架、边框和投影，避免一大片透明面覆盖设备。
- 不使用移轴景深制造微缩模型效果。主要工作视图保持清晰；预设镜头移动可打断，并尊重减少动态效果设置。

### 模型与材质

优先制作一个可信的 42U 机柜和一台 2U 服务器，再复用到场景，不同时重做所有资产。

- 机柜：窄倒角、门框、合页、门把手、立柱、导轨、底座、盲板和后部理线；穿孔门可使用抗锯齿遮罩/法线贴图，避免把每个小孔做成独立几何。
- 服务器：保留大轮廓、盘托、把手、风口、接口及电源模块层次；螺丝、标牌和网孔采用图集与贴图。装饰件与可点击业务对象分开。
- 喷涂柜体以非金属涂层处理；裸铝、镀锌件单独设置金属材质。不要把所有物体设置为中间 metalness。粗糙度增加细微变化，避免均一塑料质感。
- 先应用缩放再按米制做窄倒角；使用合适法线保持大平面平整和边缘高光。技术依据见 [Blender Bevel](https://docs.blender.org/manual/en/4.4/modeling/modifiers/generate/bevel.html)。
- 材质资产包括 base color、normal、ORM（occlusion/roughness/metallic）；近景关键资产优先 2K，共用材质/远景优先 1K，具体分辨率以屏幕尺寸验收。glTF 可存储烘焙 AO 和切线空间法线，导出节点连接需按所用 Blender 版本核对。[Blender glTF 说明](https://docs.blender.org/manual/en/4.1/addons/import_export/scene_gltf2.html)

建议调色基线（美术方向，不是实测物理反射率）：柜体石墨 `#24282D`、地板灰 `#777D82`、墙面灰白 `#D6D8D7`、铝件灰 `#AEB4B9`；绿色/琥珀色/红色仅作状态标记。材质实际输入应按色彩管理和曝光标定。

### 光照与后处理

1. 暂时关闭所有 Bloom，移除机箱发光和大面积青色地面发光，先用中性环境照明获得可读的基础画面。
2. 环境反射使用中性室内 HDR/PMREM；保留一个主阴影方向，静态环境优先烘焙 AO。避免同时提高环境、半球光、点光和曝光来补亮。
3. 保持渲染在线性空间进行，颜色贴图与非颜色数据正确区分；输出只进行一次色调映射/显示转换。当前已有 OutputPass，应检查整条链路，不能再重复加 gamma 修正。[Three.js 色彩管理](https://threejs.org/manual/pages/color-management.html)
4. 阴影覆盖范围贴合房间与观察距离，检查柜底接触阴影和面板缝隙。高画质可评估半分辨率 GTAO；其成本高于 SSAO，需要在目标硬件上比较，不直接全部开启。[GTAOPass](https://threejs.org/docs/pages/GTAOPass.html)
5. 最后只给真实 LED/灯具恢复少量辉光。可从 strength 0.1～0.25、radius 0.15～0.3、threshold 大于 1 开始试调；这些是候选参数，最终取决于线性亮度、曝光和镜头，不是通用最优值。
6. 标签、工具提示和选择信息在最终显示层绘制，避免文字被辉光或色调映射影响。保留现有 MSAA 路线，按硬件能力与性能档位选择采样数。

PBR 材质已有可用实现，关键是合理输入、环境反射和实际几何。[MeshStandardMaterial 官方说明](https://threejs.org/docs/pages/MeshStandardMaterial.html)

## 4. 拓扑 3D 单独设计

拓扑不是物理设备陈列。建议采用固定斜视或正交投影的 2.5D 分层关系图，保留深度作为层次提示，关闭默认自动旋转。

- 节点使用低反射的窄厚度面板，状态通过边标、图标和文本表达；移除每个节点的强发光顶条。
- 全图仅显示低对比关系；选中对象后突出直接上下游和完整影响路径。可以按层、租户或对象类型过滤，密集关系进行汇聚。
- 标签以屏幕像素控制尺寸、碰撞和显隐，优先展示选中对象及邻居；拥挤时聚合节点，不能无限缩小文字。
- 粒子只在选中路径、实际更新或主动演示模式出现；持续随机粒子不能暗示真实遥测流量。
- 保留 2D 作为精确查图方式。三个验收任务：找到指定服务器、追踪一个 Agent 的依赖、看清故障辐射任务；这些任务应比当前自动旋转卡片墙更容易完成。

## 5. 实现拆分和性能约束

建议将场景整理为资产加载、材质/灯光、镜头、数据叠加、拾取和资源生命周期模块。物理材质与 UI 主题解耦；所有订阅、纹理、RenderTarget 和后处理 pass 都有明确的释放入口。

| 批次 | 修改点 | 可验收产物 |
| --- | --- | --- |
| A：基础校准 | `dc3d.js` 的发光/照明/镜头；`env3d.js` 的生命周期；`build_dc_model.py` 的空调局部坐标；拓扑固定视角 | 同一模型的清晰中性画面；空调全部回到房间；无 shadow API 警告；换主题不累积资源 |
| B：资产精修 | 单柜与 2U 设备模板、倒角、材质图集、烘焙、LOD；布局源数据统一 | 总览/通道/单柜三个视角的固定截图；拉近能够分辨门框、盘位、接口和材质 |
| C：交互与性能 | 屏幕空间标签、路径过滤、共享材质/实例化、按需加载、性能档位 | 查找/追踪/影响分析可用性验证；帧时间与资源统计；静态画面按需渲染 |

重复的几何与材质尽量共享或实例化，静态环境按材质合并，可点击业务对象保留独立 ID 或拾取代理。图集与合批优先于单纯减少三角形。引入 KTX2 时同时打包本地 transcoder/WASM，登记到 `server/public-assets.json`，保持离线可用；当前仓库尚未包含这些解码资源。[KTX2Loader](https://threejs.org/docs/pages/KTX2Loader.html)

以下是下一阶段的验收目标，并非本轮测量结果：

- 在约定的桌面设备、浏览器和 1440×900 视口记录基线；标准档交互帧时间 P95 目标 ≤20 ms，低性能档目标 ≤33 ms。必须记录 GPU、DPR、采样数和 AO 开关，避免不可比的 FPS 数字。
- 默认首屏 3D 资源传输预算先设为 ≤8 MB，近景细节延迟加载；实际网格、纹理显存和绘制调用预算以性能采样调整。
- 机柜、通道和地面的边界清楚，普通表面不大片过曝；告警在无动画和色觉差异情况下仍可识别。
- 同镜头比较改造前后；至少验证浅色、深色、macOS、SpaceX 四种主题，并检查八主题的交互一致性。
- 连续切换主题 30 次、切换视图 50 次，GPU 资源计数应稳定在预热后的区间；隐藏视图停止渲染，不用定时器强制补帧。
- 设备/机柜拾取 ID、U 位、告警映射保持正确。所有美术布局变更同步源数据；不得为构图好看而挪动真实业务位置。

## 6. 下一步建议

先做“单柜 + 一段通道”的质量样板，完成中性材质、接触阴影、窄倒角、设备结构和稳定镜头，再推广到整间机房。样板应使用当前可点击对象及数据绑定，不另做脱离产品的静态效果图。

最初研究阶段未改动模型；随后交付的基础校准和 R04 样板已重建 GLB，并通过浏览器交互、32 次主题切换和 51 次视角切换验证。长时间 GPU 性能基准、整室设备精修与拓扑结构重排仍属于后续工作。
